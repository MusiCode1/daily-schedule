# פתרונות סנכרון בין מכשירים — daily-schedule

## הבעיה

כשמסנכרנים רשימות בין מכשירים, **היעדר פריט** הוא דו-משמעי:
- האם הפריט נמחק בכוונה?
- או שהמכשיר פשוט לא מעודכן?

אי אפשר להבדיל בלי מידע נוסף. תאריך עדכון לבדו לא מספיק.

### דוגמה

```
מכשיר A:  [משימה-1, משימה-2, משימה-3]
מכשיר B מוחק משימה-2:  [משימה-1, משימה-3]
מכשיר A מוסיף משימה-4:  [משימה-1, משימה-2, משימה-3, משימה-4]

סנכרון → מה עושים עם משימה-2?
```

---

## פתרון 1: Tombstones (מצבות)

### תיאור
במקום למחוק פריט מהמערך, מסמנים אותו כמחוק:

```typescript
Task {
  id: string
  name: string
  // ...
  deleted?: true
  deletedAt?: number  // timestamp של המחיקה
  deletedByDeviceId?: string
}
```

### איך המיזוג עובד

| מצב מקומי | מצב מרוחק | תוצאה |
|-----------|-----------|-------|
| פריט קיים | tombstone חדש יותר | → מחוק (המכשיר השני מחק) |
| פריט קיים | tombstone ישן יותר | → קיים (שוחזר אחרי המחיקה) |
| פריט חסר | tombstone | → מחוק (מסונכרן) |
| tombstone | פריט קיים חדש יותר | → קיים (המכשיר השני שיחזר) |

### יתרונות
- פשוט מאוד למימוש
- הפתרון הנפוץ ביותר בתעשייה (Firebase, CouchDB, Cassandra)
- עובד טוב עם הארכיטקטורה הנוכחית — רק מוסיפים שדות ל-Task/List
- מחיקה היא מידע מפורש, לא היעדר

### חסרונות
- המידע גדל עם הזמן (פריטים מחוקים נשארים)
- צריך מנגנון ניקוי (compaction) תקופתי
- Compaction בטוח רק אחרי שכל המכשירים סונכרנו

### ניקוי Tombstones
אפשר למחוק tombstones ישנים (למשל, מעל 30 יום) בתנאי שכל המכשירים הידועים סונכרנו מאז. בפרויקט שלנו, עם מספר קטן של מכשירים, זה פשוט.

## פתרון 2: Operation Log (יומן פעולות)

### תיאור
במקום לסנכרן את המצב הנוכחי (state), מסנכרנים **רשימת פעולות**:

```typescript
type Operation =
  | { type: 'add-task', listId: string, task: Task, timestamp: number, deviceId: string }
  | { type: 'edit-task', taskId: string, changes: Partial<Task>, timestamp: number, deviceId: string }
  | { type: 'delete-task', taskId: string, timestamp: number, deviceId: string }
  | { type: 'add-list', list: List, timestamp: number, deviceId: string }
  // ...
```

כל מכשיר שומר יומן של כל הפעולות שביצע. בסנכרון, מחליפים יומנים וכל צד מריץ את הפעולות החסרות.

### איך המיזוג עובד
1. כל מכשיר שולח את הפעולות שביצע מאז הסנכרון האחרון
2. הצד המקבל מריץ את הפעולות בסדר כרונולוגי
3. מחיקה היא פעולה מפורשת (`delete-task`), לא היעדר

### יתרונות
- פותר את בעיית המחיקה בצורה מושלמת — מחיקה היא פעולה, לא היעדר
- מאפשר undo/redo בחינם
- מאפשר היסטוריה מלאה של שינויים
- בסיס ל-Event Sourcing

### חסרונות
- מורכב משמעותית יותר למימוש
- דורש שינוי מהותי בארכיטקטורה (מ-state sync ל-operation sync)
- צריך לוגיקה של ordering, idempotency, ו-replay
- היומן גדל ללא הגבלה (צריך compaction)
- קונפליקטים עדיין אפשריים (שני מכשירים עורכים את אותו שדה)

## פתרון 3: Per-Item Versioning (גירסה לכל פריט)

### תיאור
כל פריט מקבל מזהה גירסה משלו שמתעדכן בכל שינוי:

```typescript
Task {
  id: string
  name: string
  // ...
  itemVersion: string    // UUID שמתחלף בכל עריכה
  lastModified: number   // timestamp
  lastModifiedByDeviceId: string
}
```

### איך המיזוג עובד
1. משווים פריט-מול-פריט לפי `id`
2. פריט שקיים בצד אחד ולא בשני:
   - אם ה-`itemVersion` שלו מוכר (ראינו אותו בעבר) → נמחק בכוונה
   - אם ה-`itemVersion` לא מוכר → פריט חדש, למזג
3. פריט שקיים בשני הצדדים עם `itemVersion` שונה → קונפליקט עריכה

### יתרונות
- Granularity טובה — קונפליקט בפריט אחד לא משפיע על אחרים
- מאפשר מיזוג חלקי (רוב הפריטים מתמזגים, רק בודדים בקונפליקט)
- לא דורש שמירת פריטים מחוקים

### חסרונות
- **דורש שמירת "known versions"** — כל מכשיר צריך לזכור אילו itemVersions הוא ראה בעבר
- יותר מורכב מ-tombstones
- עדיין לא פותר קונפליקטים של עריכה מקבילה

## פתרון 4: Merkle Chain — אימות היסטוריה משותפת

### תיאור
שרשרת hash שבה כל "כתיבה" מכילה hash של התוכן + hash של הכתיבה הקודמת:

```
write_3.hash = SHA256(content_3 + write_2.hash)
write_2.hash = SHA256(content_2 + write_1.hash)
write_1.hash = SHA256(content_1 + "genesis")
```

זה מאפשר לאמת מתמטית ששתי גירסאות חולקות היסטוריה משותפת.

### איך זה עוזר
```
מכשיר A: genesis → w1 → w2 → w3a → w4a
מכשיר B: genesis → w1 → w2 → w3b

Common ancestor = w2
שינויים מאז w2 בצד A: w3a, w4a
שינויים מאז w2 בצד B: w3b
```

ברגע שמזהים את ה-common ancestor, אפשר לבצע three-way merge (בדיוק כמו git).

### יתרונות
- מוכיח מתמטית היסטוריה משותפת
- מאפשר three-way merge מדויק
- בלתי אפשרי לזייף היסטוריה

### חסרונות
- מורכב למימוש
- דורש שמירת שרשרת ההיסטוריה (או לפחות hash chain)
- Overkill לרוב מקרי השימוש עם מספר קטן של מכשירים
- עדיין צריך לוגיקת מיזוג בפועל (ה-chain רק מזהה מה השתנה)

### קשר לפרויקט
**כבר יש לנו בסיס לזה** — שדות `writeId` + `parentWriteId` ב-ManifestV2 הם בדיוק שרשרת כזו. אם נוסיף hash של התוכן לכל writeId, נקבל Merkle chain מלא.

### ⚠️ מגבלה קריטית של `parentWriteId` בודד

הקוד הנוכחי שומר **רק את ה-manifest האחרון** ב-Google Drive. זה יוצר בעיה:

```
מכשיר A עשה:  bbb → ccc → ddd → eee
מכשיר B עשה:  bbb → fff → ggg

Drive מכיל:   { writeId: "ggg", parentWriteId: "fff" }
מכשיר A זוכר: lastKnownWriteId = "eee"
```

**כשמכשיר A מסנכרן**:
- הוא רואה `ggg` (לא מוכר)
- הוא רואה `parentWriteId: "fff"` (גם לא מוכר!)
- **הוא לא יכול לדעת ש-`fff` מצביע על `bbb`** שהוא כן מכיר

למעשה, הקוד הנוכחי עושה רק:
```typescript
if (remoteWriteId !== this.lastKnownWriteId) {
  // → CONFLICT! (בלי לבדוק היסטוריה משותפת)
}
```

### פתרונות אפשריים

**1. שמירת N manifests אחרונים ב-Drive**
```
manifest_ggg.json: { writeId: "ggg", parentWriteId: "fff" }
manifest_fff.json: { writeId: "fff", parentWriteId: "bbb" }
manifest_bbb.json: { writeId: "bbb", parentWriteId: "aaa" }
```
מכשיר A יכול לחפור אחורה בשרשרת עד שמוצא writeId מוכר.

**2. שמירת history.json קומפקטי**
```json
{
  "chains": {
    "ggg": { "parent": "fff", "contentHash": "sha256:..." },
    "fff": { "parent": "bbb", "contentHash": "sha256:..." },
    "bbb": { "parent": "aaa", "contentHash": "sha256:..." }
  }
}
```
קטן יותר מ-manifests מלאים, אבל עדיין מאפשר לעקוב אחורה.

**3. Known writeIds במכשיר + פרוטוקול חילופי מידע**
```typescript
DeviceState {
  lastKnownWriteId: "eee"
  knownWriteIds: Set<string> ["bbb", "ccc", "ddd", "eee"]
}
```
בסנכרון: שני המכשירים משווים רשימות ומזהים common ancestors.

## המלצה: Tombstones + Per-Item Versioning

השילוב המומלץ לפרויקט שלנו:

### מה מוסיפים
```typescript
Task {
  id: string
  name: string
  // שדות קיימים...

  // חדש:
  itemVersion: string        // UUID, מתחלף בכל עריכה
  deleted?: true             // tombstone
  deletedAt?: number         // מתי נמחק
}

List {
  id: string
  name: string
  // שדות קיימים...

  // חדש:
  itemVersion: string
  deleted?: true
  deletedAt?: number
}
```

### לוגיקת מיזוג
```
לכל פריט (לפי id):
  1. קיים בשני הצדדים, אותו itemVersion → אין שינוי
  2. קיים בשני הצדדים, itemVersion שונה → לוקחים את החדש יותר
  3. קיים בצד אחד, tombstone בצד שני → tombstone מנצח (אם חדש יותר)
  4. קיים בצד אחד בלבד, לא מוכר → פריט חדש, מוסיפים
  5. tombstone בשני הצדדים → נשאר מחוק
```

### למה זה מתאים
- שינוי מינימלי בקוד הקיים — רק מוסיפים שדות
- לא משנה את מבנה הגיבוי ב-Drive (רק התוכן של ה-JSON משתנה)
- פותר את בעיית המחיקה בצורה חד-משמעית
- Granularity ברמת פריט — קונפליקט במשימה אחת לא חוסם את השאר
- ניקוי tombstones פשוט עם מספר קטן של מכשירים

## פתרון 5: שמירת היסטוריה מלאה (Full History / Git-like)

### תיאור
במקום לדרוס את ה-manifest בכל backup, שומרים **snapshot של כל גירסה**. כמו Git commits.

```
manifest_writeId_aaa.json → AppState מלא בזמן T1
manifest_writeId_bbb.json → AppState מלא בזמן T2
manifest_writeId_ccc.json → AppState מלא בזמן T3
```

או בגישה יותר אופטימלית:
```
snapshot_001.json → AppState מלא
delta_002.json → רק שינויים מ-001
delta_003.json → רק שינויים מ-002
snapshot_010.json → AppState מלא (כל 10)
```

### יתרונות
- **שחזור מלא** של כל נקודה בזמן
- מאפשר **Undo** ו-**היסטוריה מלאה** לצפייה
- מקרה שימוש: "ילד מחק לוח בטעות → הורה משחזר"
- פותר לחלוטין את בעיית common ancestor — תמיד אפשר לעקוב אחורה
- מאפשר **three-way merge** אמיתי (כמו Git)

### חסרונות
- גידול בגודל הקבצים ב-Drive
- מורכבות גבוהה יותר (ניהול snapshots, deltas, cleanup)
- צריך UI להצגת ההיסטוריה והשחזור

### גודל קובץ בפועל (נתונים אמיתיים מהפרויקט)

**AppState מלא**: 48KB (3 משתמשים, מספר רשימות ומשימות)

#### אופציה א: Snapshot מלא לכל גירסה
```
10 גירסאות   = 480KB
50 גירסאות   = 2.4MB
100 גירסאות  = 4.8MB
365 גירסאות  = 17.5MB (שנה, גירסה ליום)
```

#### אופציה ב: Delta-based (רק שינויים)
כל עריכה טיפוסית:
- משימה בודדת (isDone, name) → ~150 bytes
- רשימה שלמה → ~1KB
- שינוי גדול (משתמש חדש + רשימות) → ~5KB

**ממוצע**: 300-500 bytes לגירסה

```
100 גירסאות  = 50KB
365 גירסאות  = 182KB
1000 גירסאות = 500KB
```

#### אופציה ג: היברידי (Snapshots + Deltas)
- Snapshot מלא כל 10 גירסאות
- Deltas בינתיים

**לכל 10 גירסאות**: 48KB + 9×0.5KB = 52.5KB

```
100 גירסאות  = 525KB
365 גירסאות  = 1.9MB
1000 גירסאות = 5.2MB
```

#### עם Compression (gzip)
JSON דחוס ביחס 5:1 עד 10:1:
```
2MB raw → 200-400KB gzipped
```
Google Drive API תומך ב-compression אוטומטי.

### מהירות העלאה/הורדה

| גודל | זמן (4G/WiFi) | Parsing JSON |
|------|---------------|--------------|
| 48KB (גירסה אחת) | 0.1-0.5 שניות | <10ms |
| 500KB (100 deltas) | 1-2 שניות | 20-50ms |
| 2MB (365 hybrid) | 3-5 שניות | 50-100ms |

### אסטרטגיית Rolling Window

**המלצה**: שמור 30-90 ימים, מחק/העבר לארכיון ישן יותר

```
- Snapshot מלא כל 10-20 גירסאות
- Deltas בינתיים
- מחק אוטומטית גירסאות מעל 90 יום
- או: העבר ל-"archive.json" (קובץ נפרד, נטען רק לפי דרישה)
```

**תוצאה טיפוסית**: 500KB - 2MB

### מקרה שימוש: שחזור אחרי מחיקה

UI אפשרי:
```
[Timeline של גירסאות]
2026-02-10 14:30 - עזרא מחק "לוח בוקר" ❌
2026-02-10 12:15 - אבישי הוסיף משימה "שיעורי בית"
2026-02-09 18:00 - שכנא סיים "לוח ערב" ✅

[כפתור: שחזר ללוח מ-12:15]
```

## אלטרנטיבה קלת משקל: Soft Delete + Restore Window

במקום היסטוריה מלאה, פשוט לא מוחקים ממש:

```typescript
List {
  // ...
  deleted?: true
  deletedAt?: number
}

// UI: "רשימות שנמחקו (30 יום אחרונים)"
//     [כפתור שחזור]
```

**יתרונות על פני Full History**:
- הרבה יותר פשוט למימוש
- אפס תוספת גודל (פריט מחוק = כמה bytes)
- עדיין מאפשר שחזור תוך X ימים
- לא צריך UI מורכב של timeline

**חסרונות**:
- רק מחיקות, לא היסטוריה של **עריכות**
- לא מאפשר "ראה מה היה בלוח לפני שבוע"

## סיכום מורחב

| גישה | גודל (100 גירסאות) | מהירות | מורכבות | יכולות |
|------|---------------------|---------|----------|---------|
| Tombstones בלבד | 48KB | מהיר מאוד | פשוט | מיזוג מחיקות |
| Per-Item Version | 48KB | מהיר מאוד | בינוני | מיזוג granular |
| Soft Delete + Restore | 48KB | מהיר מאוד | פשוט | שחזור מחיקות (30 יום) |
| **Full History (Deltas)** | **50KB** | **מהיר מאוד** | **גבוה** | **שחזור מלא + timeline** |
| Full History (Hybrid) | 525KB | מהיר | גבוה | שחזור מלא + timeline |
| Full History (Snapshots) | 4.8MB | איטי | גבוה | שחזור מלא + timeline |

### המלצה מדורגת

**שלב 1 (מינימום viable)**: Tombstones + Soft Delete
- פשוט, מהיר, עובד
- מאפשר שחזור מחיקות תוך 30 יום
- מספיק לרוב המקרים

**שלב 2 (אם רוצים יותר)**: Per-Item Versioning
- מוסיף יכולת מיזוג granular
- עדיין קל משקל

**שלב 3 (אם רוצים timeline מלא)**: Full History עם Deltas + Rolling Window
- שומר 90 ימים אחרונים
- Delta-based = גודל מינימלי (~500KB)
- מאפשר UI של "מה קרה בשבוע שעבר"
- דורש פיתוח UI ולוגיקה של delta calculation
