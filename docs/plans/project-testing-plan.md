# תוכנית בדיקות לפרויקט `daily-schedule`

תאריך: 2026-02-16  
סטטוס: בתכנון/יישום הדרגתי

מטרת המסמך: להגדיר שיטת בדיקות אחידה, ישימה וניתנת למדידה לפרויקט, כך שנוכל לזהות רגרסיות מוקדם ולהעלות גרסאות בביטחון.

---

## 1) מטרות איכות

1. למנוע שבירה של זרימת הליבה: בחירת משתמש, עבודה על לוח משימות, סימון/ביטול משימות.
2. להבטיח תאימות לאחור בטעינה של נתונים קיימים (Migration + Device State).
3. לשמור יציבות בגיבוי/שחזור Google Drive ובתהליכי סנכרון.
4. לשמר חוויית שימוש יציבה במכשירי יעד (קיוסק/טאבלט), כולל מצבי אופליין בסיסיים.
5. לאפשר שחרור גרסה עם Gate ברור (מה חייב לעבור לפני פריסה).

---

## 2) היקף הבדיקות (Scope)

### בתוך ההיקף

1. שכבת נתונים: `stores`, `services`, `migration`, `persistence`.
2. שכבת לוגיקה: `logic/*Controller*`.
3. שכבת תצוגה: `routes`, `components`.
4. אינטגרציות קריטיות: Drive Backup V2, PWA Service Worker, אודיו/TTS.

### מחוץ להיקף (בשלב זה)

1. עומסים גבוהים (Load/Stress) בקנה מידה ייצור.
2. אוטומציה מלאה ל-Google OAuth אמיתי ב-CI.
3. בדיקות אבטחה מתקדמות (Penetration Testing מלא).

---

## 3) אסטרטגיית בדיקות (Test Pyramid)

### שכבה A: בדיקות סטטיות (בכל שינוי)

1. Type + Svelte checks  
   פקודה: `npm run check`
2. פורמט ולינט  
   פקודה: `npm run lint`

מטרה: לעצור שגיאות בסיסיות לפני הרצת בדיקות כבדות.

### שכבה B: Unit Tests (מהירות, לוגיקה טהורה)

1. הרצה: `npm run test:unit -- --run`
2. מיקוד:
   - `migration` ו-`deviceState` migrations
   - `drive/crypto`, `drive/backupPayloads`
   - שירותים דטרמיניסטיים (ללא תלות UI)

מטרה: לכסות כללים עסקיים וחישובים בצורה מהירה ואמינה.

### שכבה C: Integration Tests (שילוב שירותים)

1. הרצה תחת Vitest (Node) עם Mocks/Fakes.
2. מיקוד:
   - `driveBackupV2.integration.test.ts`
   - `dailyScheduleBackupRepo.cache.test.ts`
   - תרחישי שמירה/טעינה עם מבני state ישנים

מטרה: לוודא שהתלויות בין מודולים עובדות כיחידה אחת.

### שכבה D: Component/Browser Tests

1. שימוש בפרויקט `client` ב-Vitest Browser.
2. מיקוד:
   - קומפוננטות Svelte קריטיות עם אינטראקציה
   - תרחישי RTL בסיסיים ותצוגת מצבי שגיאה

מטרה: לתפוס שבירות UI מוקדם, בלי מחיר של E2E מלא.

### שכבה E: E2E (Playwright)

1. הרצה: `npm run test:e2e`
2. תרחישי ליבה:
   - Login/בחירת משתמש
   - מעבר למסך `/tasks`
   - סימון משימה ואימות עדכון UI
   - פתיחת מסכי הגדרות עיקריים

מטרה: לאמת שהמערכת עובדת מקצה לקצה כמו משתמש אמיתי.

### שכבה F: בדיקות ידניות ממוקדות סיכון

1. PWA install/offline בסיסי.
2. Google Drive אמיתי (חיבור/גיבוי/שחזור/קונפליקט).
3. בדיקות UX על טאבלט/מסך קיוסק.

מטרה: לכסות אזורים שקשה או לא יציב לאוטומציה מלאה.

---

## 4) מבנה תיקיות בדיקות (בפועל)

הבדיקות מופרדות מקוד האפליקציה תחת:

```txt
sveltekit-version/tests/
  component/
  unit/
  integration/
  fixtures/
```

עקרון עבודה:

1. אין יצירת `*.test.ts` או `*.spec.ts` חדשים תחת `src/`.
2. `src/` נשאר לקוד מוצר בלבד.
3. כל Fixture בדיקות נשמר תחת `tests/fixtures`.

---

## 5) מטריצת כיסוי לפי תחומי מוצר

1. **לוח משימות (`/tasks`)**  
   Unit ללוגיקה, Component לתצוגה, E2E לזרימה מלאה.
2. **ניהול משתמשים/רשימות**  
   Unit ל-Stores, Component לטפסים, E2E ליצירה/עריכה בסיסית.
3. **תמונות ו-Crop (IndexedDB + ImageDisplay)**  
   Unit לטרנספורמציות/metadata, ידני לרינדור ויזואלי.
4. **אודיו וחיזוקים (Random + TTS fallback)**  
   Unit לבניית רצפים + ידני לאימות חוויית שמע.
5. **Google Drive Backup V2**  
   Integration + Unit קיימים, ידני על Drive אמיתי לפני שחרור.
6. **מיגרציות State**  
   Unit מבוסס fixtures לכל גרסה היסטורית נתמכת.
7. **PWA**  
   בדיקות ידניות + Lighthouse + E2E בסיסי של offline אחרי טעינה ראשונית.

---

## 6) סביבות בדיקה ונתוני בדיקה

1. סביבת פיתוח מקומית: להרצות את כל השכבות לפני merge משמעותי.
2. סביבת Preview/Dev branch: Smoke מלא לפני העלאה ל-production.
3. נתוני בדיקה:
   - Fixtures לגרסאות state ישנות.
   - משתמשי בדיקה עם רשימות קצרות/ארוכות.
   - תרחישי תמונות (עם ובלי `idb:`).
4. כלל פרטיות: אין להשתמש בנתוני משתמש אמיתיים במסמכי בדיקה/fixtures.

---

## 7) Gate לשחרור גרסה (Definition of Ready to Release)

לפני `deploy`:

1. `npm run check` עובר.
2. `npm run lint` עובר.
3. `npm run test:unit -- --run` עובר.
4. `npm run test:e2e` עובר או שיש חריג מאושר ומתועד.
5. בוצעה בדיקה ידנית קצרה:
   - `/tasks` נטען ועובד.
   - כניסה להגדרות עובדת.
   - אם השינוי נוגע ל-Drive/PWA: בוצעה גם בדיקת Smoke ייעודית בתחום.
6. `docs/walkthrough.md` מעודכן עם מה נבדק בפועל ומה לא.

---

## 8) תדירות והרצות מומלצות

1. בכל PR/שינוי משמעותי:
   - `npm run check`
   - `npm run test:unit -- --run`
2. לפני merge ל-branch ראשי:
   - `npm run lint`
   - `npm run test:e2e`
3. לפני פריסת production:
   - כל הסעיפים ב-Gate לשחרור
   - בדיקות ידניות ממוקדות סיכון

---

## 9) סדר עדיפויות לתוספת בדיקות (Backlog)

1. להרחיב E2E עבור זרימת `/tasks` כולל Edit Mode מלא.

3. להוסיף בדיקות Component למסכי הגדרות רגישים (Users/Lists/People).
4. להוסיף מטריקות כיסוי (Coverage) ויעד התחלתי לשירותים קריטיים.

## 10) קריטריוני הצלחה לתוכנית

1. ירידה בכמות רגרסיות פונקציונליות אחרי merge.
2. קיצור זמן גילוי באגים (בשלב PR במקום אחרי פריסה).
3. עקביות בין מה שכתוב במסמכי התכנון לבין מה שנבדק בפועל ב-release.
4. יכולת שחזור תקלות מהירה בעזרת fixtures ותרחישים מתועדים.
