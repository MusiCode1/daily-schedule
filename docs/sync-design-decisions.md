## 3. מקרי קצה של מיזוג — צריך להגדיר

### כללי מיזוג שהוסכמו

| תרחיש                                          | התנהגות                                |
| ---------------------------------------------- | -------------------------------------- |
| שני צדדים שינו **פריטים שונים**                | מיזוג אוטומטי (שני השינויים חלים)      |
| צד אחד **הוסיף** פריט, השני לא                 | הפריט נוסף                             |
| צד אחד **מחק** רשימה                           | **הרשימה נשארת מחוקה** — מחיקה גוברת   |
| שני צדדים שינו **אותו פריט**                   | last-write-wins (לפי timestamp)        |
| צד אחד מחק רשימה, צד שני הוסיף משימה **לתוכה** | הרשימה נשארת מחוקה. המשימה החדשה אובדת |

### אלגוריתם מיזוג: 3-way merge

**החלטה**: לא מטפלים בכל מקרה קצה בנפרד. משתמשים ב-**3-way merge גנרי** (כמו git):

```
      ancestor (common)
       /          \
      A            B
       \          /
        merged
```

1. מצא common ancestor בהיסטוריה
2. חשב `diff(ancestor, A)` ו-`diff(ancestor, B)`
3. שדות שונים → מזג (שניהם חלים)
4. אותו שדה → קונפליקט → last-write-wins

### מקרים שנבדקו ונסגרו

| מקרה | איך 3-way merge מטפל | סטטוס |
|------|----------------------|--------|
| שינוי סדר + הוספת משימה | שני diffs שונים, מתמזגים | נסגר |
| שינוי שם משתמש + שינוי הגדרות | שדות שונים באותו object, מתמזג | נסגר |
| UUID כפול | כמעט בלתי אפשרי. אם קורה — last-write-wins | נסגר |
| isDone + שינוי שם משימה | **ערוצים נפרדים** — isDone ב-progress, שם ב-content | נסגר |
| העברת משימה בין רשימות | בדלתא: delete מרשימה א' + add לרשימה ב'. עובד | נסגר |

## 4. נושאים טכניים שנדונו

### מערכים מקוננים vs Objects (פרכה 6)

**הבעיה**: AppState משתמש במערכים:

```typescript
lists[userId] = List[]    // מערך
list.tasks = Task[]       // מערך
```

כש-jsondiffpatch מייצר דלתות על מערכים, הוא מתבסס על **אינדקסים**. אם מכשיר A הוסיף פריט באינדקס 3 ומכשיר B הוסיף פריט באינדקס 3, הדלתא מתנגשת.

**פתרון אפשרי 1 — objectHash**:

jsondiffpatch תומך ב-`objectHash` שמזהה אובייקטים לפי `id` במקום אינדקס:

```typescript
const differ = jsondiffpatch.create({
  objectHash: (obj) => obj.id
});
```

יתרון: אין שינוי ב-AppState. חסרון: צריך לוודא שזה עובד טוב עם כל הרמות.

**פתרון אפשרי 2 — מעבר ל-objects**:

```typescript
// במקום
tasks: Task[]
// לעבור ל-
tasks: { [taskId: string]: Task }
```

יתרון: פותר את הבעיה לצמיתות, גם ללא ספרייה ספציפית. חסרון: דורש מיגרציה.

**החלטה סופית (2026-02-11):** **מעבר ל-objects** + שדה `order` מפורש.

```typescript
List {
  id: string
  name: string
  tasks: { [taskId: string]: Task }  // ← object במקום מערך
  // ...
}

Task {
  id: string
  name: string
  order: number  // ← סדר מפורש (0, 1, 2...)
  // ...
}
```

**נימוק:**
- פותר את בעיית האינדקסים לצמיתות
- עובד עם כל ספריית diff (לא תלוי ב-objectHash)
- lookup מהיר יותר (O(1))
- **normalization אחרי merge** מטפל בכפילויות זמניות של order

**מיגרציה:** v14 → v15 (ראה סעיף 8)

### דחיסה (gzip)

**החלטה: לא דוחסים ידנית כרגע.**

**העברה (Transport)**:
- Google Drive API תומך ב-`Accept-Encoding: gzip` — ההעברה עצמה דחוסה **אוטומטית**
- כלומר: גם בלי שנעשה כלום, ה-JSON עובר דחוס בצינור
- זה מה שמשפיע על מהירות הסנכרון — לא הגודל בדרייב

**אחסון (Storage)**:
- הקובץ בדרייב נשמר כפי שהועלה (לא דחוס)
- גם 5MB בדרייב = לא בעיה (Google Drive נותן 15GB)
- אם בעתיד הגודל יגדל → אפשר לדחוס עם CompressionStream API

**מסקנה**: דחיסה ידנית היא סתם תקורה בשלב הזה. ה-transport compression מספיק.

### ETags — optimistic locking

Google Drive API תומך ב-ETags:

```
1. הורד קובץ → קבל ETag "abc"
2. העלה גרסה חדשה עם If-Match: "abc"
3. אם מישהו כתב בינתיים → שגיאה 412 (Precondition Failed)
4. תוריד שוב, תמזג, תנסה שוב
```

זה פותר את בעיית הכתיבה הבו-זמנית בלי locks.

### תמונות

- תמונות נשמרות **בינארית** כקבצים נפרדים בגוגל דרייב (לא base64)
- הדלתות וה-snapshots כוללים רק **מזהים** (`imageSrc: "idb:xxx"`)
- אם דלתא מפנה לתמונה שעדיין לא הורדה → מוצג ספינר עד שהתמונה מורדת
- ה-hydration/dehydration הנוכחי (base64) צריך להיות מוחלף

### CRDTs (Automerge/Yjs) — למה לא מתאים *כרגע*

- מיועדים ל-**real-time collaboration** (כמו Google Docs)
- כבדים (~100-200KB לספרייה)
- מניחים ערוץ תקשורת ישיר (WebSocket/WebRTC)
- הפרויקט שלנו = סנכרון **אסינכרוני** דרך Google Drive כ-storage
- הארכיטקטורה שלנו דומה יותר ל-**Git** מאשר ל-Google Docs

**עתידי**: כשנרצה real-time (טלוויזיה מסונכרנת עם אייפד), CRDTs/Yjs **כן יתאימו** כשכבה נפרדת. ראה סעיף "ארכיטקטורת שתי שכבות" למטה.

### ערוצי סנכרון: Content vs Progress

**תובנה חשובה**: הקוד הקיים כבר מפריד את הנתונים בגיבוי ל-3 קבצים:

```
ContentV2   → רשימות, משתמשים, הגדרות (בלי isDone!)
ProgressV2  → רק { taskDone: { [taskId]: boolean } }
AssetsIndex → תמונות
```

**משמעות**: שני ערוצי סנכרון נפרדים:

| ערוץ | נתונים | אסטרטגיית סנכרון | מורכבות |
|------|--------|-------------------|---------|
| **progress** | isDone בלבד | **last-write-wins, בלי היסטוריה** | אפסית |
| **content** | רשימות, משתמשים, הגדרות | **היסטוריה + דלתות + 3-way merge** | עיקר העבודה |

**למה זה מפשט?** רוב הכתיבות היומיומיות (ילד מסמן isDone) הולכות ל-progress — שהוא trivial לסנכרן. ה-content משתנה הרבה פחות (רק כשהורה מגדיר לוח).

### ארכיטקטורת שתי שכבות (נוכחי + עתידי)

```
שכבה 1: Google Drive (אסינכרוני) — נוכחי
  → סנכרון בין sessions, גיבוי, היסטוריה
  → עובד גם offline
  → Content: דלתות + 3-way merge
  → Progress: last-write-wins

שכבה 2: WebSocket/WebRTC (real-time) — עתידי
  → סנכרון טלוויזיה ↔ אייפד באותו חדר
  → Yjs/Automerge מתאימים כאן
  → רץ מעל אותו AppState
```

שתי השכבות לא סותרות. שכבה 1 = source of truth לטווח ארוך. שכבה 2 = אופטימיזציית latency.

## 5. הנחות עבודה שהתגלו

הנחות שהיו מוסוות ונחשפו בדיון:

1. **משתמש יחיד לחשבון** — אבל בפועל, ההורה והילד עובדים מול אותו חשבון. ההורה מגדיר, הילד מסמן. זה **לא** שני משתמשים עצמאיים.
1. **אין צד שרת** — כל התעבורה בצד לקוח. אין locks, אין coordinator, אין transactions (חוץ מ-ETags של גוגל דרייב).
1. **קונפליקט אמיתי הוא נדיר** — כי בד"כ הורה וילד עושים דברים שונים (הגדרות vs סימון isDone). אבל **אפשרי** כשההורה מגדיר לוח מחר בזמן שהילד עדיין סיים את היום.
1. **הנתונים קטנים** — 48KB ל-state מלא. גם עם צמיחה, סביר ש-state לא יעבור 200-300KB לחשבון.
1. **הסנכרון לא real-time** — מספיק שהוא יקרה "בערך עכשיו" (כמה שניות latency). אין צורך ב-real-time ברמת מילישניות.
1. **ההיסטוריה לא נמחקת** — אין rolling window. עם דחיסה, שנים של היסטוריה = עשרות KB עד מגהבייטים בודדים.
1. **מתג נעילת ילדים** — פתרון טוב יותר מהצגת קונפליקטים. ילד יכול לסמן isDone בלבד, לא לערוך מבנה.
1. **progress = ערוץ נפרד** — הקוד הקיים כבר מפריד isDone לקובץ progress.json. זה מפשט מאוד את מערכת הסנכרון כי רוב הכתיבות היומיומיות הן trivial.
1. **דחיסה בדרך מספיקה** — Google Drive API דוחס transport אוטומטית. לא צריך לדחוס ידנית. גם 5MB בדרייב = לא בעיה.
1. **real-time = שכבה עתידית נפרדת** — סנכרון טלוויזיה ↔ אייפד דרך WebSocket/Yjs. לא משפיע על הארכיטקטורה של שכבה 1 (Google Drive).

## 6. זרימת סנכרון מתוכננת (סקיצה)

```
1. הורד metadata מגוגל דרייב (appProperties → writeId)
2. אם writeId = lastKnownWriteId שלי → אין שינוי remote
   → אם יש שינויים מקומיים → העלה
3. אם writeId ≠ lastKnownWriteId → יש שינוי remote
   → הורד state.json + history.json (במקביל, request אחד כל אחד)
   → מצא common ancestor בהיסטוריה
   → מזג את השינויים
   → העלה state.json + history.json (עם ETag לוודא שלא נדרסנו)
   → אם ETag fail (412) → חזור לשלב 1
4. הכל קורה ברקע, בלי אזהרות למשתמש
```

## 7. מבנה קבצים בגוגל דרייב (סקיצה)

interface SyncHistory {

### 8.3. טריגרי סנכרון

הסנכרון יופעל ב-3 תרחישים:

1. **בטעינת האפליקציה** - בדיקה מול Google Drive
2. **אחרי שינוי מקומי** - debounce 5 שניות (כמו היום)
3. **visibility change** - כשחוזרים לטאב/אפליקציה

**לא** polling תקופתי (לא צריך).

### 8.4. טיפול בשגיאות רשת

**Retry Logic:**
- **10 ניסיונות** עם exponential backoff
- זמנים: 1s, 2s, 4s, 8s, 16s, 32s, 64s, 128s, 256s, 512s
- **סה"כ ~17 דקות** של ניסיונות
- אחרי 10 כשלונות → ויתור (ננסה בטריגר הבא)

**UI מצב סנכרון:**
- **אייקון קבוע** בפינה (🟢🟡🔴⚪)
  - 🟢 **ירוק** - מסונכרן (אחרון: לפני X דקות)
  - 🟡 **צהוב** - מסנכרן עכשיו...
  - 🔴 **אדום** - כשל (ננסה שוב בעוד X שניות)
  - ⚪ **אפור** - offline (אין אינטרנט)
- **לחיצה על האייקון** - פרטים מלאים (סנכרון אחרון, ניסיון X/10, שינויים מקומיים)

**תור offline:**
- השינויים כבר ב-AppState (מקור אמת)
- הסנכרון = "best effort" ברקע
- כשהרשת חוזרת → 3-way merge אוטומטי

### 8.5. למה לא Tombstones בשלב 1?

**תובנה קריטית:** אם שומרים היסטוריה **לנצח** (ללא ניקוי), tombstones **לא נחוצים** ל-3-way merge!

**ההיסטוריה מספיקה:**
```
Common ancestor: { 'a': {...}, 'b': {...}, 'c': {...} }
מכשיר A: { 'a': {...}, 'c': {...} }  // 'b' נעלם
מכשיר B: { 'a': {...}, 'b': {...}, 'c': {...} }  // 'b' קיים

3-way merge: 'b' היה ב-common, נעלם ב-A → מחיקה מפורשת!
```

**Tombstones יתווספו ב-v16 רק עבור:**
- UI שחזור נוח ("פריטים שנמחקו - לחץ לשחזר")
- rolling window (אם נחליט לנקות היסטוריה בעתיד)

### 8.6. נורמליזציה של order אחרי merge

**בעיה פוטנציאלית:** שני מכשירים עושים drag & drop במקביל → כפילויות ב-`order`.

**פתרון:** normalization אחרי כל merge:
```typescript
function normalizeTaskOrder(tasks: { [id: string]: Task }) {
  const sorted = Object.values(tasks).sort((a, b) => {
    if (a.order !== b.order) return a.order - b.order;
    return a.id.localeCompare(b.id); // tie-breaker
  });

  sorted.forEach((task, index) => {
    task.order = index;
  });
}
```

**תוצאה:** גם אם יש כפילויות, ה-normalization מתקן.
